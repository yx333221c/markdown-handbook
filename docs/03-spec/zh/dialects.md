# 方言：同一份 md，换个地方就变样

> English: [en/dialects.md](../en/dialects.md)

同一段 Markdown，在 Pandoc 里转 docbook、在 GitHub wiki 里渲染、在 Discourse 帖子里发出去，结果可能对不上。谁都没写错，三份「标准」本来就没对齐过。

Gruber 在 Daring Fireball 上写的是一页语法说明，讲设计目标，留了大量空白。`Markdown.pl` 是这份说明的第一个实现，Perl 写的，脚本自己的行为又和说明有出入，还带着 bug，2004 年 12 月 17 日之后就没再更新。后来的 CommonMark、GFM 是正式规范，一条条把边界写死，可它们定稿时，各站点早按各自的理解跑了多年。所以你现在手里至少有三套参照：那页说明、脚本的实际行为、后来的规范。三者不一致，谁也没法把谁撤回去。

## 没有语法错误，差异就藏得住

CommonMark 里「任意字符序列都是合法文档」。解析器遇到拿不准的写法不会报错，只会挑一种解释，安静输出 HTML。于是 `- a` 后面跟两空格还是三空格、`*` 没闭合时强调吃到哪里、同名链接定义用哪一个，这些分歧不会在编辑时冒出来。你把文档发到另一个平台，读者看到的是另一副样子，往往要等别人问「这段怎么少了标题」才发现。这也是 CommonMark 要把几百个边界情况配成期望 HTML 的原因，见 [zh/commonmark.md](commonmark.md)。

Pandoc、Reddit、Stack Overflow、Discourse 各有取舍：面向学术出版的会往引用、表格、多格式导出那边加东西，论坛更在意用户内容的安全和贴代码的体验。具体差在哪条语法上，得拿实际输入去比，凭印象列清单容易写错。

要比就上 Babelmark。它把同一段源码喂给 20 多个实现，并排列出各自的 HTML 输出。你怀疑某段写法在目标站点会走样，贴进去看一眼，比翻文档快。

## 怎么写才尽量 portable

几条能直接照做的：

- 只用核心语法。段落、标题、列表、强调、链接、代码这些各家都认的写法打底，别依赖某个站点独有的标记。
- 表格、任务列表、删除线、扩展自动链接这些是 GFM 加的，用到的地方写清楚「依赖 GFM」，别默认别人那边也有，见 [zh/gfm.md](gfm.md)。
- 原始 HTML 能不用就不用。GitHub 那套后处理会过滤一批标签，别的平台规则又不一样，贴进去等于把排版交给运气。
- 发布前在目标平台预览一次。README 传 GitHub、帖子发论坛，各看各的最终渲染。本地编辑器的预览只代表它自己。

语法层面的坑在 [zh/gotchas.md](../../02-syntax/zh/gotchas.md)，链接和图片的写法在 [zh/links-and-images.md](../../02-syntax/zh/links-and-images.md)。

## 标准化没让方言消失，也不必消失

CommonMark 出了十多年，GFM 也发了正式规范，Pandoc、Reddit、Discourse 还是各跑各的。原因不玄：这些站点要解决的问题不一样。论坛得先挡住用户贴进来的脚本和乱七八糟的标签，出版工具得把同一份稿子导成 docbook、LaTeX、EPUB，GitHub 得让 README 和 issue 在同一套渲染里安全显示。强行统一到一份规范，等于让其中一堆需求迁就另一堆，换不来什么。手里的文档要跨平台，就用上面那几条把差异压小，够用了。
